# 基于 DuckDB 的 Olist 电商离线数据仓库建设

## 📌 项目简介
本项目基于巴西 Olist 电商公开数据集（包含约 10 万笔订单、9 张原始表），使用轻量级分析型数据库 DuckDB，从零搭建了一套标准的企业级离线数据仓库。
项目严格按照 **ODS（贴源层） -> DWD（明细层） -> DWS（服务层） -> ADS（应用层）** 的四层架构进行开发，完成了从数据抽取、清洗转换到业务报表产出的全链路 ETL 流程。

## 🛠️ 技术栈
*   **数据库**：DuckDB (列式存储分析引擎)
*   **开发语言**：SQL (包含窗口函数、CTE、多维聚合等高级语法)
*   **架构模型**：Kimball 维度建模、四层数仓架构

## 🏗️ 数据仓库架构设计

1.  **ODS 贴源层**：使用 `read_csv_auto` 原样加载 4 张核心业务表（订单、明细、客户、商品），不做任何修改。
2.  **DWD 明细层**：进行多表 `JOIN` 整合，构建明细宽表。主要完成以下数据清洗与防御：
    *   **无效数据过滤**：剔除未送达（非 `delivered`）状态的订单，保证 GMV 准确；过滤 2016 年之前的异常时间戳。
    *   **防脏数据兜底**：使用 `COALESCE` 将缺失的运费和价格填充为 0，防止 `NULL` 值导致后续加法运算崩溃；将缺失的商品类目兜底为 `'unknown'`。
    *   **维度规范化**：使用 `TRIM` 去除城市和类目字段的首尾空格，防止由于空格导致的维度分裂。
3.  **DWS 服务层**：按业务维度进行轻度汇总，避免 ADS 层重复扫描海量明细。
    *   构建了基于 **时间（年月）**、**地域（州/城市）**、**商品品类** 三个核心维度的汇总表。
    *   使用 `COUNT(DISTINCT customer_unique_id)` 准确计算真实的人均消费（ARPU），规避了原始数据中 `customer_id` 订单级代理键的陷阱。
4.  **ADS 应用层**：直接面向业务场景产出可视化报表。
    *   **全局大盘趋势表**：分析每月 GMV 和客单价变化。
    *   **地域营收排行表**：各州业绩排行与客单价对比。
    *   **畅销品类 Top 10**：明确过滤 `'unknown'` 类目，定位核心盈利商品。
    *   **城市下钻明细表**：利用窗口函数 `RANK() OVER(PARTITION BY...)`，动态计算出各个州内部销售额排名前三的城市。

## 📁 文件结构
*   `ODS.sql`：贴源层建表与数据加载脚本。
*   `DWD.sql`：明细数据清洗与整合脚本。
*   `DWS.sql`：多维度轻度汇总脚本。
*   `ADS.sql`：业务报表生成脚本。

## 💡 核心亮点
*   **防御性 ETL 开发**：代码中内置了针对空值、脏文本和异常时间的 6 道防御机制，保证了下游报表的绝对健壮性。
*   **准确的人头计算**：深入理解 Olist 数据集特性，解决了常见的 ARPU 计算失真问题。
*   **灵活的维度下钻**：未将州名硬编码在 SQL 中，而是通过窗口函数一次性计算出全国各州内部的城市 Top N 排名。
